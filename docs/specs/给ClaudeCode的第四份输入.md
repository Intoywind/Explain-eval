# 给 Claude Code 的第四份输入：长请求验证

2026-11-11。先把手上的事做完（第四组 original_eval × luna、四组汇总、盲标包 `blind/round1/`），再做这一份。

## 为什么做

三组里 gpt-6.1-sol 有 91% 的回答把卡点全答上了，两份 Skill 分不出高下。Xia 的判断：现在的题比真实使用简单，一次只讲一个知识点、回答约两千字；真实使用时一次要讲好几个知识点，模型的错多出在长输出里。

这一步只验证一件事：**同样的知识点、同样的卡点，从“一次讲一个”换成“一次讲五个”，答上率会不会掉。** 掉了，后面的测试题就按长题来出；没掉，说明难度不在长度上，要换方向。所以这一步不出新题，只把已有的题拼起来。

## 1. 生成回答

- 只跑两组：general_v1 × gpt-6.1-sol、general_v1 × gpt-6-luna。每条长请求重复 3 次，一共 36 次调用。
- 发给被测模型的内容和短条目的拼法完全一致（同一份 Skill 做 system，读者设定、请求、材料的拼法不变）。**不要加任何关于篇幅、详略的话**，要看的就是模型自己会不会因为内容多而讲得更省。
- 被测模型的参数不变（sol：reasoning.effort medium；luna：reasoning.effort 和 verbosity 都是 medium）。
- 输出上限：短回答 sol 平均 1714 个输出 token，长回答预计是它的 3 到 5 倍，而且上限里含推理 token。先看现在的上限设的是多少，调到不会截断的值（建议不低于 32000），请求超时也相应放宽。
- 截断的回答（API 返回未完成、原因是输出上限）记为失败，不送裁判，报告里单独列份数。不要用截断的回答凑数。
- 这批调用要和原来 30 条短条目的调用分得开（单独的 run 标记或单独的条目文件标记都行），原来四组的报告数字不能因为这批数据变化。

## 2. 判分

- 裁判用 `prompts/judge_v2.md`，不改 prompt。每份长回答判一次，卡点和步骤就用 `items_long_dev.jsonl` 里的。
- 裁判的输出会比以前长（最多 11 个卡点加 23 个步骤，每项都带引句），把裁判的输出上限也调到不会截断。
- 引句校验、重判、`needs_review` 的规则都不变。
- 另外随机抽 12 份（每组 6 份，固定随机种子并记下来）判第二遍，报告两遍之间卡点、步骤的一致率。长回答加长清单，裁判稳不稳要单独确认。

## 3. 报告（单独一份，不要并进四组汇总）

对比的另一边是已有的正式评分：同一组（general_v1 × sol、general_v1 × luna）在短条目上的 judge_v2 结果（ECON-003 用重判后的）。

1. **逐卡点对比表**（51 行 × 2 组）：按 `items_long_dev_map.json` 对上，每行给出这个卡点单独讲时的答上次数（3 次里几次）和连着讲时的答上次数（3 次里几次）。这张表**不套知识清零**，直接用裁判对每个卡点的 `answered`；长请求里某一部分讲错不该把另外四部分的卡点一起清掉。
2. **汇总**：每组的卡点答上率，短 vs 长；有多少个卡点下降、持平、上升；按第 1 到第 5 部分分别算一遍（看是不是越靠后掉得越多）；按课程、按读者版本各算一遍。
3. **步骤**：同样做 103 个步骤的短 vs 长对比，只要汇总和按部分的分解，逐条表放附录。
4. **“卡点全部答上”的占比**：长回答里卡点全部答上的份数 ÷ 总份数。短的一边给两个数：每份短回答卡点全答上的占比（已有）；以及把同一门课、同一版本的 5 份短回答当成一份来看时全答上的占比（按重复序号配对：第 1 次重复的 5 份算一份，以此类推）。
5. **篇幅**：每份长回答的字数和输出 token 数；和对应的 5 份短回答字数之和比，是多少比例。能按“第 i 部分”的标题把长回答切开的话，再给每一部分的字数和对应短回答字数的比例。
6. **知识错误和没答全**：长回答里触发知识错误的份数、是哪一部分；`incomplete` 的份数、漏了什么（特别是有没有整部分没讲的）。
7. `needs_review` 的份数和清单；重判次数；生成和判分各自的实际花费。
